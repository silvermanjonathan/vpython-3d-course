Opener · 10 minutes

Retrieval: graphs, functions, and loops

Paper first. Three questions about things you already know, because every one of them does a job in today's programs.

Question: A point on a graph is written (2, 3). Which number says how far across, and which says how far up?

The first number, 2, is across. The second number, 3, is up. Today every place gets a third number that says how far toward you, so a place is three numbers instead of two.

def hello(name):
    print("hello", name)

Question: Does the print line run when Python reads the def, or only later?

Only later, when something calls hello. The def makes the function and stores it under the name hello. Today you write functions that you never call yourself. VPython calls them when a key goes down or the mouse is clicked.

Question: What does a while loop do that an if gate does not?

It repeats. The gate checks its condition once and runs its body once or not at all. The loop checks its condition before every pass and runs the body again each time the condition is True. Every program today ends with a loop whose condition is always True, so it runs until you stop it.

Chunk 1 of 8

One line makes a world

VPython is a library: a file of functions that someone else wrote. from vpython import * gives your program every one of them. sphere() makes a ball and opens a browser tab to show it. The tab is where the pictures go. The terminal still shows what you print.

Every object has a pos: three numbers that say where its middle is. The program never gives the sphere a pos, so it gets the starting value.

from vpython import *

ball = sphere()
print("the ball is at", ball.pos)
print("its radius is", ball.radius)

Predict: The program never says where to put the ball. The first print line shows ball.pos as three numbers. What are the three numbers, and what is the radius?

What it actually prints (run without a browser)

the ball is at <0, 0, 0>
its radius is 1.0

All three numbers are 0, printed as <0, 0, 0>. That is the middle of the world, and the camera looks straight at it. The radius is 1. Both are the starting values VPython gives a sphere when you do not say otherwise. Right-drag inside the tab to turn the camera, and scroll to zoom. Close the tab, or press Ctrl+C in the terminal, when you are done looking.

Chunk 2 of 8

Three numbers for every place

vec(2, 0, 0) is a vector: three numbers held in one value, in the order x, y, z. x is how far to the right. y is how far up. z is how far toward you, out of the screen. A negative number goes the other way: left, down, or away from you.

You can add two vectors. Each number adds to its own partner: x with x, y with y, z with z. Adding vec(0, 3, 0) to a pos leaves x and z alone and raises y by 3.

The three arrows are the axes. Red points along x, green along y, blue along z. Keep them in your programs until the directions feel obvious.

from vpython import *

arrow(axis=vec(3, 0, 0), color=color.red)
arrow(axis=vec(0, 3, 0), color=color.green)
arrow(axis=vec(0, 0, 3), color=color.blue)

crate = box(pos=vec(2, 0, 0), color=color.orange)
print("crate is at", crate.pos)

crate.pos = crate.pos + vec(0, 3, 0)
print("crate is now at", crate.pos)

crate.pos = crate.pos + vec(-2, 0, -4)
print("and now at", crate.pos)

Predict: The last pos line adds vec(-2, 0, -4). Which of the three numbers change? And where does the crate end up: left or right of where it was, higher or lower, closer to you or farther away?

What it actually prints (run without a browser)

crate is at <2, 0, 0>
crate is now at <2, 3, 0>
and now at <0, 3, -4>

x and z change. y stays 3.

Left or right: left, by 2. x goes from 2 to 0, so the crate is straight above the middle of the world.

Higher or lower: neither. The y number did not change, so the crate is still 3 up.

Closer or farther: farther away, by 4. z goes from 0 to -4, and negative z is away from you. The output box shows <0, 3, -4>. Turn the camera with a right-drag and you can see the crate sitting behind the arrows.

Chunk 3 of 8

pos is the middle, so things sink

A box has a size: three numbers for how long, how tall, and how deep it is. Each of the three starts at 1 when you do not say. pos is the middle of the box, not its bottom. A box 1 tall with its pos at y = 0 reaches from y = -0.5 up to y = 0.5.

The ground here is a wide, flat box. Its middle is at y = -0.1 and it is 0.2 tall, so its top face is at y = 0. Put a crate at y = 0 and half of the crate is under the ground.

crate.pos.y is the y number on its own. You can read it, and you can assign to it.

from vpython import *

ground = box(pos=vec(0, -0.1, 0), size=vec(10, 0.2, 10), color=color.green)
crate = box(pos=vec(0, 0, 0), color=color.orange)
print("crate middle is at y =", crate.pos.y)
print("crate bottom is at y =", crate.pos.y - crate.size.y / 2)

crate.pos.y = 0.5
print("after the fix, crate bottom is at y =", crate.pos.y - crate.size.y / 2)

Predict: The ground's top face is at y = 0 and the crate's pos is at y = 0. How much of the crate is under the ground? And after the fix line, what number is in crate.pos.y, and where is the bottom of the crate?

What it actually prints (run without a browser)

crate middle is at y = 0.0
crate bottom is at y = -0.5
after the fix, crate bottom is at y = 0.0

Half of the crate is under the ground. pos is the middle and the crate is 1 tall, so its bottom is at y = -0.5, which the second output line shows.

After the fix, crate.pos.y is 0.5. That lifts the middle by half the height, so the bottom is at y = 0.0, exactly on the ground. A taller crate needs a bigger lift: half of its height, every time.

Chunk 4 of 8

The loop at the bottom, and why rate(30) is in it

A program that has reached its last line is finished. VPython's own instructions say to end every program with a loop that never stops, so the program keeps running and can keep listening for keys and clicks. while True: is that loop. Its condition is always True, so the body runs pass after pass until you close the tab or press Ctrl+C in the terminal.

rate(30) is the one line the loop must have. It makes the loop pause so that it runs 30 passes in a second and no more, which leaves the computer time to draw the picture between passes.

Everything else in the body happens once per pass. Move the ball by 0.1 on every pass and it travels 3 in one second.

from vpython import *

ball = sphere(color=color.yellow)
passes = 0

while True:
    rate(30)
    passes = passes + 1
    ball.pos.x = ball.pos.x + 0.1
    if passes == 30:
        print("after", passes, "passes the ball is at", ball.pos)
    if passes == 60:
        print("after", passes, "passes the ball is at", ball.pos)

Predict: Thirty passes take one second. How far along x has the ball moved after one second, and how far after two? Say what you would see in the tab.

What it actually prints (run without a browser, quit after 60 passes of the loop)

after 30 passes the ball is at <3, 0, 0>
after 60 passes the ball is at <6, 0, 0>

After one second x is 3: thirty passes, and 0.1 added on each one. After two seconds x is 6. The output box shows <3, 0, 0> and then <6, 0, 0>.

In the tab, the ball slides to the right and keeps going until you stop the program. The number in rate is the passes per second, so rate(60) with the same 0.1 would move the ball twice as fast.

Chunk 5 of 8

A key press is an event, and a function answers it

Pressing a key is an event: something that happens while the program runs, at a moment the program does not choose. You do not call the function yourself. You bind it. scene.bind("keydown", paint) tells VPython to call paint every time a key goes down. Write the function's name without brackets, because you are naming it, not calling it.

VPython calls the function with one argument, the event. evt.key is the name of the key as a string: "r", "g", "left", "up", and so on. Three flat gates compare it with the three letters. A key that none of the gates name changes nothing.

The tab only hears keys when it has the focus. Click inside the 3D scene once before pressing anything. The caption line above the scene is there to remind you.

from vpython import *

scene.caption = "Click the 3D scene, then press r, g, or b."
ball = sphere(color=color.white)

def paint(evt):
    if evt.key == "r":
        ball.color = color.red
    if evt.key == "g":
        ball.color = color.green
    if evt.key == "b":
        ball.color = color.blue
    print("key pressed:", evt.key, " ball colour is now", ball.color)

scene.bind("keydown", paint)

while True:
    rate(30)

Predict: Three keys are pressed in turn: g, then b, then x. What colour is the ball after each one? Which of the three print lines shows a colour that did not change, and why did that line print at all?

What it actually prints (run without a browser, quit after 10 passes of the loop)

key pressed: g  ball colour is now <0, 1, 0>
key pressed: b  ball colour is now <0, 0, 1>
key pressed: x  ball colour is now <0, 0, 1>

Fed in by the build script: the g key pressed on pass 2, the b key pressed on pass 5, the x key pressed on pass 7.

After g the ball is green and the print shows <0, 1, 0>. A colour is a vector too: red, green, and blue, each from 0 to 1. After b the ball is blue, <0, 0, 1>. After x the ball is still blue.

The third print line shows the colour that did not change, the same <0, 0, 1> as the second. It printed because paint runs on every key press: VPython calls it for x the same way it calls it for g and b. The three gates decide whether a colour is assigned, and for x all three are False, so the print line is the only line in the body that runs.

Chunk 6 of 8

Holding a key down

A keydown event happens once per press. Hold the arrow down and nothing more happens. For a box that keeps moving while the key is held, ask a different question on every pass: keysdown() returns a list of the keys that are down right now. "right" in keys is True on every pass while the right arrow is held.

This program has no bound function. The four gates are inside the loop, so they run 30 times a second, and every pass with the key held adds speed once more.

The print line runs only on passes where the list is not empty, so the terminal shows one line per pass while a key is held and nothing in between.

from vpython import *

scene.caption = "Click the 3D scene, then hold an arrow key."
floor = box(pos=vec(0, -0.1, 0), size=vec(12, 0.2, 12), color=color.green)
player = box(pos=vec(0, 0.5, 0), color=color.orange)
speed = 0.2

while True:
    rate(30)
    keys = keysdown()
    if "right" in keys:
        player.pos.x = player.pos.x + speed
    if "left" in keys:
        player.pos.x = player.pos.x - speed
    if "up" in keys:
        player.pos.z = player.pos.z - speed
    if "down" in keys:
        player.pos.z = player.pos.z + speed
    if len(keys) > 0:
        print(keys, "player is at", player.pos)

Predict: The right arrow is held down for three passes, then let go, then the up arrow is held for one pass. Which of the three pos numbers changes while right is held, and by how much in total? When up is held, does the z number go up or down, and does the box rise?

What it actually prints (run without a browser, quit after 10 passes of the loop)

['right'] player is at <0.2, 0.5, 0>
['right'] player is at <0.4, 0.5, 0>
['right'] player is at <0.6, 0.5, 0>
['up'] player is at <0.6, 0.5, -0.2>

Fed in by the build script: the right arrow key held on passes 3 to 5, the up arrow key held on pass 8.

While right is held, the first number, x, changes: by 0.6 in total, 0.2 on each of the three passes. The output box shows x at 0.2, then 0.4, then 0.6.

When up is held, z goes down, from 0 to -0.2. The up arrow is wired to the gate that subtracts speed from player.pos.z, and negative z is away from you, so the box moves away across the floor. The box does not rise: y stays 0.5 on every line. To make the up arrow lift the box instead, change player.pos.z to player.pos.y in that gate and change the minus to a plus.

Chunk 7 of 8

Clicking on a thing

A click is an event too. Bind a function to "click". Inside it, scene.mouse.pick is the object that was under the mouse at the moment of the click. The house word for this object is the pick.

When the mouse is over empty space there is no object, and the pick is None. None is Python's value for nothing. The gate if thing is None: catches that case. Without it, the colour line would try to colour nothing, and the program would stop with an error that starts AttributeError: 'NoneType' object has no attribute 'color'.

The seven boxes have no names of their own. The pick is whichever one was clicked, and thing is its name inside the function. A right-drag turns the camera and is not a click, so the function does not run for it.

from vpython import *

scene.caption = "Click a box. Then click the gap between two boxes."
for x in range(-3, 4):
    box(pos=vec(x * 1.5, 0, 0), color=color.cyan)

def clicked(evt):
    thing = scene.mouse.pick
    if thing is None:
        print("clicked empty space")
    else:
        thing.color = color.red
        print("clicked the box at", thing.pos)

scene.bind("click", clicked)

while True:
    rate(30)

Predict: The first click lands on the box whose pos is <1.5, 0, 0>. The second lands in the gap between that box and the middle one. What does the program print for each click, and does any box change colour on the second click?

What it actually prints (run without a browser, quit after 6 passes of the loop)

clicked the box at <1.5, 0, 0>
clicked empty space

Fed in by the build script: a click at (1.5, 0, 0) on pass 2, a click at (0.75, 0.1, 0) on pass 4.

First click: it prints clicked the box at <1.5, 0, 0>, and that box turns red. The pick is the box, so the else branch runs.

Second click: it prints clicked empty space. The pick is None, the gate on None is True, and the else branch does not run, so no box changes colour.

Chunk 8 of 8

Buttons and sliders

A widget is a control that appears under the scene: a button, a slider, a checkbox, a menu. Each one is made with a function call, and each takes a bind= argument naming the function to run when the widget is used.

The bound function receives the widget itself. For a slider, s.value is the number it is set to. For a button there is nothing to read: the click is the message.

scene.append_to_caption adds words under the scene, so the slider has a label beside it. The Reset button puts the ball's pos and radius back to their starting values, however many times the ball was nudged.

from vpython import *

ball = sphere(color=color.magenta)

def reset(b):
    ball.pos = vec(0, 0, 0)
    ball.radius = 1
    print("Reset clicked: pos", ball.pos, " radius", ball.radius)

def resize(s):
    ball.radius = s.value
    print("slider moved to", s.value)

def nudge(evt):
    if evt.key == "right":
        ball.pos.x = ball.pos.x + 1
        print("nudged to", ball.pos)

button(text="Reset", bind=reset)
scene.append_to_caption("   Size: ")
slider(min=0.2, max=3, value=1, bind=resize)
scene.bind("keydown", nudge)

while True:
    rate(30)

Predict: The right arrow is pressed twice, the slider is dragged to 2.5, and then Reset is clicked. Where is the ball, and how big is it, after each of those four events?

What it actually prints (run without a browser, quit after 8 passes of the loop)

nudged to <1, 0, 0>
nudged to <2, 0, 0>
slider moved to 2.5
Reset clicked: pos <0, 0, 0>  radius 1.0

Fed in by the build script: the right arrow key pressed on pass 2, the right arrow key pressed on pass 3, the widget bound to resize set to 2.5 on pass 5, the widget bound to reset clicked on pass 7.

After the first press the pos is <1, 0, 0>. After the second it is <2, 0, 0>. The radius is still 1 for both, because nudge touches only x.

The slider sets the radius to 2.5, and the ball grows but stays at x = 2, because resize touches only the radius.

Reset puts the pos back to <0, 0, 0> and the radius back to 1, and the last output line shows both. The slider's knob stays where you dragged it, because the program did not move it. Drag it again and the ball grows again.

Build · 10 minutes

Build: a block builder

You are making a small building game. There is a green floor, 16 wide and 16 deep, with its top face at y = 0. A left-click on the floor puts a block there, standing on the floor. A click on a block that is already standing puts a new block on top of it. A paint pot block in the corner holds the colour of the next block, and a menu under the scene changes it. A Reset button clears the floor. The camera still turns with a right-drag and zooms with the scroll wheel, so a builder can walk around the model.

  1. Start from the card below: the floor, the three camera lines, the build function bound to "click", and the loop.
  2. Add a paint pot: pot = box(pos=vec(-7, 0.5, 7), color=color.red), above the function. In build, give each new block color=pot.color. Then add menu(choices=["Red", "Blue", "Yellow", "White"], bind=pick_colour) under the scene. Its bound function gets the menu as m, and m.selected is the chosen word. Four flat gates, one per word, each assigning pot.color.
  3. Stacking: in build, add a second gate for a click on a block. When the pick is not None and is not the floor and is not the pot, place the new block at hit.pos + vec(0, 1, 0).
  4. Reset: make an empty list blocks = [] above the function, and append every block you place: blocks.append(box(...)). A Reset button's function loops over the list, sets b.visible = False on each block, then empties the list with blocks.clear().
  5. Put a caption above the scene that says what a left-click does and what a right-drag does.

Where on the floor did the click land?

The pick says which object was clicked. It does not say where on that object. scene.mouse.project answers that: it finds the point where the click lands on a flat plane. normal=vec(0, 1, 0) says the plane faces up, and point=vec(0, 0, 0) says it passes through the middle of the world, which is where the floor's top face is. round moves each number to the nearest whole number, so the blocks line up on a grid.

The three camera lines matter. scene.forward tilts the camera so it looks down at the floor instead of straight along it. scene.autoscale = False and scene.range = 8 stop the camera from zooming out on its own every time a block is added.

from vpython import *

scene.caption = "Click the floor to place a block."
scene.autoscale = False
scene.range = 8
scene.forward = vec(0, -0.6, -1)
floor = box(pos=vec(0, -0.1, 0), size=vec(16, 0.2, 16), color=color.green)

def build(evt):
    hit = scene.mouse.pick
    if hit is floor:
        spot = scene.mouse.project(normal=vec(0, 1, 0), point=vec(0, 0, 0))
        print("floor click at", spot)
        box(pos=vec(round(spot.x), 0.5, round(spot.z)), color=color.red)
        print("block placed at", vec(round(spot.x), 0.5, round(spot.z)))

scene.bind("click", build)

while True:
    rate(30)

Predict: Three clicks. The first lands on the floor at (3.2, 0, -1.8). The second lands on the block that the first click placed. The third lands on the floor at (-6.49, 0, 6.51). How many blocks are standing at the end, and where is the third click's block?

block placed at <3, 0.5, -2>

Setup and how this page was checked

VPython 7.6.5 installs with pip install vpython and runs on Python 3.8 to 3.12. On a newer Python the import fails before anything is drawn, with ModuleNotFoundError: No module named 'pkg_resources'; as of October 2026 the fix is on GitHub but not yet released, so keep the room on Python 3.12 and, if the error appears, run pip install "setuptools<81" once. Key events do not reach a program that runs inside a Jupyter notebook, so run every file from the VS Code terminal. The output boxes on this page come from running each snippet against the installed library with no browser open and the keys and clicks fed in by the build script. The picture itself is not checked, so run the page's programs once on the projector machine before class.

Open the terminal in VS Code and install the library: pip install vpython. Check it worked with python -c "import vpython". It should print nothing at all and give you the prompt back. A traceback here is an install problem, not a problem with your program.
