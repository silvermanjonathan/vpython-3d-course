Opener · 5 minutes

Retrieval: pick any stamp

Talk this one out with a neighbour.

Question: Pick any stamp on your ledger card and say, in one sentence each: what it lets a program do, and which session's build used it.

Any stamp works. Two examples: keysdown() lets a program move something for as long as a key is held, and the car in session 4 used it to drive. scene.mouse.pick lets a click find the object under the mouse, and the editor in session 9 used it to grab.

Question: Three functions in a program need to share one number. Where does it live?

On an object, as an attribute: sun.factor, floor.held, player.score. Any function that can see the object can read it and change it.

Chunk 1 of 4

A knob block: the numbers you will want to change, named, at the top

Every program has numbers that get tuned: how fast, how big, how strong. Give each one a name in capitals at the top of the file, and use the name everywhere below. Then tuning the program is changing one line, and the lines below say what they mean.

This program is session 3's bouncing ball with its three numbers lifted into a knob block. Nothing below the block has a bare number in it that you might want to change.

from vpython import *

GRAVITY = 9.8
BOUNCE = 0.8
START_HEIGHT = 6

ground = box(pos=vec(0, -0.1, 0), size=vec(10, 0.2, 10), color=color.green)
ball = sphere(pos=vec(0, START_HEIGHT, 0), radius=0.5, color=color.yellow)
ball.vel = vec(0, 0, 0)
dt = 1 / 30
passes = 0
print("knobs: gravity", GRAVITY, " bounce", BOUNCE, " start height", START_HEIGHT)

while True:
    rate(30)
    passes = passes + 1

    ball.vel.y = ball.vel.y - GRAVITY * dt
    ball.pos = ball.pos + ball.vel * dt

    if ball.pos.y < ball.radius:
        ball.pos.y = ball.radius
        ball.vel.y = -ball.vel.y * BOUNCE
        print("bounce on pass", passes, "  going up at", round(ball.vel.y, 2))

Predict: Which one line would you change to make the ball bounce higher each time, and which to make it fall faster? Would either change need a second line changed anywhere below?

What it actually prints (run without a browser, quit after 100 passes of the loop)

knobs: gravity 9.8  bounce 0.8  start height 6
bounce on pass 32   going up at 8.36
bounce on pass 83   going up at 6.64

Bounce higher: BOUNCE = 0.8, to a number closer to 1. Fall faster: GRAVITY = 9.8, to a bigger number. Neither needs any other line changed, because every line below uses the name, not the number.

The output box shows the first bounce on pass 32 at 8.36 per second and the second on pass 83. On a bigger START_HEIGHT the first bounce would come later and faster, and again nothing else would change.

Chunk 2 of 4

A skeleton that runs before it does anything

The first version of a project has every object it will need, the knob block, the empty functions it will need, the bind lines, and the loop with nothing in it but rate(30). It runs, it shows the scene, and it does nothing else. That is the first thing to make, because every mistake in it is a mistake you can see before any gate is written.

The objects go in a list called things, so that later a Reset and a count can reach all of them.

from vpython import *

SPEED = 0.2

scene.caption = "Nothing works yet. That is on purpose."
ground = box(pos=vec(0, -0.1, 0), size=vec(16, 0.2, 16), color=color.green)
things = []
things.append(box(pos=vec(0, 0.5, 0), color=color.orange))
things.append(sphere(pos=vec(3, 0.5, -2), radius=0.5, color=color.cyan))
things.append(cone(pos=vec(-3, 0, 2), axis=vec(0, 1.5, 0), radius=0.5, color=color.red))

def tapped(evt):
    print("a key was tapped:", evt.key, " (nothing wired to it yet)")

scene.bind("keydown", tapped)
print("skeleton is up:", len(things), "things on the ground, and the loop is running")

while True:
    rate(30)

Predict: The loop body is only rate(30). What does the program do when it runs, and what happens when a key is tapped?

What it actually prints (run without a browser, quit after 4 passes of the loop)

skeleton is up: 3 things on the ground, and the loop is running
a key was tapped: left  (nothing wired to it yet)

Fed in by the build script: the left arrow key pressed on pass 2.

It draws the ground and the three things, prints that the skeleton is up, and then runs the loop 30 times a second doing nothing, so the scene stays on screen and can be turned with the mouse.

A tap calls tapped, which prints the key and nothing else. The output box shows the left arrow arriving. The function is already bound, so wiring the key is a matter of adding gates to a function that already runs.

Chunk 3 of 4

One feature, then run, then the next

Add one thing to the skeleton. Run it. Check it against what you expected. Only then add the next thing. A program with three new features and a bug has three places the bug could be; a program with one new feature and a bug has one.

This is the skeleton with its first feature: the left and right keys move the first thing. The second and third things are still waiting.

from vpython import *

SPEED = 0.2

ground = box(pos=vec(0, -0.1, 0), size=vec(16, 0.2, 16), color=color.green)
things = []
things.append(box(pos=vec(0, 0.5, 0), color=color.orange))
things.append(sphere(pos=vec(3, 0.5, -2), radius=0.5, color=color.cyan))
things.append(cone(pos=vec(-3, 0, 2), axis=vec(0, 1.5, 0), radius=0.5, color=color.red))
passes = 0

while True:
    rate(30)
    passes = passes + 1
    keys = keysdown()

    if "right" in keys:
        things[0].pos.x = things[0].pos.x + SPEED
    if "left" in keys:
        things[0].pos.x = things[0].pos.x - SPEED

    if passes == 5:
        print("feature 1 check: box at", things[0].pos, "  ball still at", things[1].pos)

Predict: Before running: write down where the box should be after right is held for three passes, and where the ball should be. Then run and compare.

What it actually prints (run without a browser, quit after 5 passes of the loop)

feature 1 check: box at <0.6, 0.5, 0>   ball still at <3, 0.5, -2>

Fed in by the build script: the right arrow key held on passes 2 to 4.

The box should be at x = 0.6, three passes of 0.2, and the ball should not have moved from <3, 0.5, -2>. The output box shows both. If the ball had moved, the gate would be touching the wrong thing, and with only one feature added, that is the only place to look.

Write the expected value down first, every time. A check you make up after seeing the output is not a check.

Chunk 4 of 4

The caption tells the player what to do

The caption is the first thing someone else sees. It says what the keys and the mouse do, in the order they will want them. \n inside a string starts a new line. Write the caption at the top of the file, before anything is built, because writing it is the fastest way to find out what the program is for.

from vpython import *

scene.caption = "Arrow keys move the box.\nClick a shape to change its colour.\nPress r to put everything back.\n"
ground = box(pos=vec(0, -0.1, 0), size=vec(16, 0.2, 16), color=color.green)
print(scene.caption)

Predict: How many lines does the caption have under the scene, and what does \n do inside the string?

What it actually prints (run without a browser)

Arrow keys move the box.
Click a shape to change its colour.
Press r to put everything back.

Three lines. \n is the new-line character: wherever it appears, the text goes on to the next line. The output box shows the same three lines in the terminal, because the print shows the string the way the caption shows it.

A caption that says three things is a plan for three features. If you cannot write the caption, the plan is not finished.

The plan sheet

Four boxes on paper, filled in before the skeleton is typed:

  1. What the viewer sees. The objects, in a list, with their starting places.
  2. The controls. Each key, click, slider or button, and what it does. This becomes the caption.
  3. What the program remembers. Every number or thing that changes while it runs, and where it lives: a plain variable in the loop, or an attribute on which object.
  4. The knobs. The numbers you will want to tune, with names.

Hinge question · from today's chunks

Before you build

Question: A student's plan sheet says the controls are: arrows move the player, space fires, r restarts, a slider for speed, and a Delete mode tick box. The program has two bound functions, a slider function, a checkbox function, and a loop. Which of the five controls go in the loop with keysdown, which go in a bound function, and which numbers from the sheet have to live on an object rather than in a plain variable?

Arrows go in the loop with keysdown, because moving should continue while the key is held. Space and r go in a bound keydown function, because each should happen once per tap. The slider and the checkbox have their own bound functions.

Anything the slider or checkbox function changes has to live on an object: the speed and the delete flag. Anything that only the loop reads and changes can be a plain variable. The restart is the hard case: if r is in a bound function, every number it resets has to be on an object too; if r is read with keysdown in the loop instead, they can stay plain variables, which is what session 7 did.

Card A: three camera views on three keys

Each number key sets where the camera looks and which way it faces. The views are written once at the top, as three pairs of vectors, so changing a view is changing one line.

from vpython import *

VIEW_1 = [vec(0, 0, 0), vec(0, -0.5, -1)]
VIEW_2 = [vec(4, 0, 0), vec(-1, -0.3, 0)]
VIEW_3 = [vec(0, 2, 0), vec(0, -1, -0.2)]

scene.caption = "Press 1, 2 or 3 to change the view."
ground = box(pos=vec(0, -0.1, 0), size=vec(16, 0.2, 16), color=color.green)
tower = cylinder(pos=vec(4, 0, 0), axis=vec(0, 3, 0), radius=0.5, color=color.white)
scene.autoscale = False
scene.range = 8

def view(evt):
    if evt.key == "1":
        scene.center = VIEW_1[0]
        scene.forward = VIEW_1[1]
    if evt.key == "2":
        scene.center = VIEW_2[0]
        scene.forward = VIEW_2[1]
    if evt.key == "3":
        scene.center = VIEW_3[0]
        scene.forward = VIEW_3[1]
    print("key", evt.key, "  camera looks at", scene.center, "  facing", scene.forward)

scene.bind("keydown", view)

while True:
    rate(30)

Predict: 2 is pressed, then 3, then x. After the x, where does the camera look? Why does the print line run for x at all?

What it actually prints (run without a browser, quit after 6 passes of the loop)

key 2   camera looks at <4, 0, 0>   facing <-1, -0.3, 0>
key 3   camera looks at <0, 2, 0>   facing <0, -1, -0.2>
key x   camera looks at <0, 2, 0>   facing <0, -1, -0.2>

Fed in by the build script: the 2 key pressed on pass 1, the 3 key pressed on pass 3, the x key pressed on pass 5.

After x the camera still looks at <0, 2, 0>, facing <0, -1, -0.2>, the third view, because none of the three gates named x and nothing changed. The print line runs for every key, because it is after the gates and not inside any of them, so the output box has three lines.

View 2 looks at the tower from the side, and view 3 looks straight down at the middle of the ground. The number keys arrive as the strings "1", "2" and "3".

Card B: blocks that fall, and a player that dodges

A game that is the catch game turned around: the blocks are the danger and the player has to not be under them. The hit gate is the catch gate from session 7. A hit costs a life and sends the block back to the top. The blocks are a list, each with its own velocity, so one loop serves all of them. For this test run the player starts directly under the lowest block, so the first hit is certain; in the game the player starts in the middle and dodges.

from vpython import *
from random import randint

FALL_SPEED = 4
REACH = 1.0

ground = box(pos=vec(0, -0.1, 0), size=vec(12, 0.2, 6), color=color.green)
player = box(pos=vec(0, 0.5, 0), size=vec(1, 1, 1), color=color.blue)
player.lives = 3
blocks = []
for i in range(3):
    b = box(pos=vec(randint(-5, 5), 8 + i * 4, 0), color=color.red)
    b.vel = vec(0, -FALL_SPEED, 0)
    blocks.append(b)
player.pos.x = blocks[0].pos.x
dt = 1 / 30
passes = 0

while True:
    rate(30)
    passes = passes + 1
    keys = keysdown()

    if "right" in keys:
        player.pos.x = player.pos.x + 0.3
    if "left" in keys:
        player.pos.x = player.pos.x - 0.3

    for b in blocks:
        b.pos = b.pos + b.vel * dt
        gap = abs(b.pos.x - player.pos.x)
        if b.pos.y < 1 and gap < REACH:
            player.lives = player.lives - 1
            print("hit on pass", passes, "  lives left", player.lives)
            b.pos = vec(randint(-5, 5), 12, 0)
        if b.pos.y < -0.5:
            b.pos = vec(randint(-5, 5), 12, 0)

Predict: Three blocks start at heights 8, 12 and 16, all falling at 4 per second, from random x positions, and the player is under the lowest one. On about which pass is the first hit? Will the second block hit too?

What it actually prints (run without a browser, quit after 60 passes of the loop)

hit on pass 53   lives left 2

Pass 53. The lowest block reaches height 1 after falling 7 units, which at 4 per second is 1.75 seconds, and pass 53 is the first pass past that. Lives go from 3 to 2.

Whether the second block hits depends on where randint put it, and this run stops on pass 60 before it arrives. If its x is more than 1 from the player's x, the gap gate is False, the block falls past, and the second gate sends it back to the top with no print. A block that misses is not a bug; it is the game.

Card C: a windmill farm with a wind slider and a pause box

Every blade is in a list, and one loop turns them all by the wind speed, which lives on the ground as ground.wind so the slider can change it. The checkbox sets ground.paused, and the loop turns nothing while it is True.

from vpython import *

WIND = 3

ground = box(pos=vec(0, -0.1, 0), size=vec(20, 0.2, 20), color=color.green)
ground.wind = WIND
ground.paused = False
blades = []
for x in [-6, 0, 6]:
    cylinder(pos=vec(x, 0, 0), axis=vec(0, 3, 0), radius=0.2, color=color.white)
    blade = box(pos=vec(x, 3, 0.3), size=vec(3, 0.3, 0.1), color=color.red)
    blades.append(blade)

def set_wind(s):
    ground.wind = s.value
    print("wind is now", ground.wind)

def set_pause(c):
    ground.paused = c.checked
    print("paused is now", ground.paused)

scene.append_to_caption("Wind: ")
slider(min=0, max=10, value=WIND, step=1, bind=set_wind)
scene.append_to_caption("   ")
checkbox(text="Pause", bind=set_pause)
turned = 0
passes = 0

while True:
    rate(30)
    passes = passes + 1

    if ground.paused == False:
        for blade in blades:
            blade.rotate(angle=radians(ground.wind), axis=vec(0, 0, 1))
        turned = turned + ground.wind

    if passes in [30, 60, 90]:
        print("pass", passes, "  each blade has turned", turned, "degrees in total")

Predict: The wind slider is set to 6 right after pass 30 and the pause box is ticked right after pass 60. How many degrees has each blade turned by pass 30, by 60, and by 90?

What it actually prints (run without a browser, quit after 90 passes of the loop)

pass 30   each blade has turned 90 degrees in total
wind is now 6
pass 60   each blade has turned 270 degrees in total
paused is now True
pass 90   each blade has turned 270 degrees in total

Fed in by the build script: the widget bound to set_wind set to 6 on pass 31, the widget bound to set_pause set to True on pass 61.

90 degrees by pass 30: 3 per pass. 270 by pass 60: 180 more, at 6 per pass. Still 270 by pass 90, because the blades were paused after pass 60 and the loop turned nothing after that.

The gate ground.paused == False is around both the rotate and the counter, so pausing stops both. Untick the box and the blades carry on from where they stopped.

Running this in VS Code

Once, before the first run

Open the terminal in VS Code and install the library: pip install vpython. Check it worked with python -c "import vpython". It should print nothing at all and give you the prompt back. A traceback here is an install problem, not a problem with your program.

Every run after that

Save your file as YourName_vpython10.py: your first name, an underscore, then vpython10. Run it from the terminal. The 3D scene opens in a new browser tab, sometimes behind VS Code, so look for it before deciding that nothing happened. Click inside the scene before pressing any key. To end the program, close the tab or press Ctrl+C in the terminal. The program is written to run until you do. Run the file again and you get a fresh tab.

VPython draws solid shapes that you can turn and zoom. Everything you print still goes to the terminal, and everything you draw goes to the browser tab. Words in the terminal, pictures in the tab.
